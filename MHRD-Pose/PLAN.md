# Diagnostic Plan: MHR Skeleton Rendering Mismatch & Non-Converging MPJPE

## Symptoms

1. **GT mesh rendering in `debug_vis.py`**: The pink MHR mesh and yellow SMPL joint markers don't align correctly with the person in the input images.
2. **MPJPE not converging**: 850mm after 2 epochs (expected ~50-100mm for a working model).
3. **PA-MPJPE stable at ~151mm**: Suggests global alignment is off but local pose is roughly correct.
4. **`loss_keypoints_3d` stuck at ~3.2**: Not decreasing across epochs.
5. **`loss_keypoints` (2D) at ~1.5**: Higher than expected for a HRNet-based model.
6. **`loss_regr_pose` at ~1.68**: MHR pose parameter regression is not learning.
7. **`loss_shape` at ~0.85**: Vertex reconstruction is partially working.

---

## Root Cause Analysis

### Issue 1: Coordinate Space Mismatch in 3D Keypoint Loss

**Location**: `mhr_losses.py:276-295`

The 3D keypoint loss compares:
- **pred**: `joints3d_smpl` from `mhr_head.py` — SMPL joints computed from **predicted** MHR vertices via barycentric interpolation. These are in **body-local space** (MHR origin at feet, Y-up).
- **gt**: `joints3d` (i.e., `joints3d_smpl` computed in `mhr_trainer.py:124-141`) — SMPL joints computed from **GT** MHR vertices via the same barycentric interpolation. Also in **body-local space**.

**Verdict**: Both are in the same body-local space. The loss formulation is **correct** in terms of coordinate space. However, the **barycentric mapping itself** may be inaccurate — the `mhr2smpl_mapping.npz` maps MHR vertices to SMPL joint locations, but if the MHR mesh topology differs significantly from SMPL, the barycentric interpolation at joint locations may produce systematically wrong joint positions.

### Issue 2: MHR Skeleton Joint Ordering Mismatch

**Location**: `mhr_constants.py:32`, `mhr_head.py:170-172`

- MHR skel_state has **127 joints** (line 170: `skel_state[:, :, :3]` → `[B, 127, 3]`)
- `NUM_MHR_SKELETON_JOINTS = 22` (mhr_constants.py:32)
- SMPL has **24 joints**

The `MHR_JOINT_NAMES` list (22 joints) has a different ordering and count than SMPL joints. When the fallback path in `mhr_losses.py:288-293` uses `joints3d` (MHR skel_state joints), it takes the first 22 MHR skeleton joints which **do not correspond** to SMPL joint indices [0-23].

**However**, the active path uses `joints3d_smpl` (24 joints from barycentric mapping), so this fallback is not triggered. Still, the MHR skel_state joint ordering is fundamentally different from SMPL.

### Issue 3: GT Pose Parameter Conversion Mismatch

**Location**: `dataset_wrapper.py:188-284`, `scripts/preconvert_to_mhr.py:156-171`

The GT `lbs_model_params` (pose) come from the SMPL→MHR conversion:
```python
result = converter.convert_smpl2mhr(
    smpl_vertices=smpl_vertices,
    return_mhr_parameters=True,
    return_mhr_vertices=True,
)
lbs_model_params = mhr_params.get('lbs_model_params', torch.zeros(batch_size, 204))
```

The converter finds MHR pose parameters that **reproduce SMPL vertices**. But the model predicts MHR pose parameters that **directly fit the image**. These are different optimization objectives:
- Converter: "Find MHR pose that gives SMPL vertices" (inverse kinematics)
- Model: "Find MHR pose that explains the image" (vision)

If the MHR skeleton structure doesn't match SMPL's skeleton, the converted pose parameters will be **inconsistent** with what the model learns to predict. The model predicts pose from image features, and the GT pose was generated by a converter that may produce pose values in a different "effective" space.

### Issue 4: Barycentric Mapping Accuracy

**Location**: `assets/mhr2smpl_mapping.npz`

The mapping converts MHR vertices (12826 verts, LOD1) to SMPL vertices (6890) using triangle IDs and barycentric coordinates, then applies SMPL's J_regressor to get 24 joints. If:
- The MHR mesh vertex ordering doesn't match the expected format
- The barycentric coordinates are inaccurate
- The SMPL J_regressor doesn't align with MHR's skeleton

Then the GT SMPL joints will be systematically offset from where the model predicts them.

### Issue 5: Debug Vis GT Mesh Rendering — Global Orient Handling

**Location**: `debug_vis.py:290-296`

```python
_go = to_numpy(item['pose'])[:3]  # axis-angle [3]
_R_go = _ScipyR.from_rotvec(_go).as_matrix()
_R_180x = np.diag([1., -1., -1.])
_R_net = _R_180x @ _R_go
gt_verts_np = gt_verts_np @ _R_net.T
```

This applies `R_180x @ R_global_orient` to GT vertices. But GT vertices from the MHR converter are already in the MHR canonical frame (facing forward, origin at feet). The global_orient from the original SMPL data describes the person's orientation in the **world** frame, not the body frame. Applying it to MHR vertices may produce incorrect orientation.

**For datasets where GT `pose` has `global_orient = [0,0,0]`** (common in BEDLAM), this code path produces `_R_net = R_180x`, and vertices get the 180°X flip. This is correct for the renderer (which also applies 180°X). But if the pose's global_orient is non-zero (e.g., from datasets with actual body rotation), the combined rotation may not produce the expected orientation.

### Issue 6: Preconversion skel_state Extraction Ambiguity

**Location**: `scripts/preconvert_to_mhr.py:184-193`

```python
if skel.ndim == 4 and skel.shape[-2:] == (4, 4):
    joints = skel[:, :, :3, 3] * 0.01
elif skel.ndim == 3 and skel.shape[-1] >= 16:
    joints = skel[:, :, 12:15] * 0.01
elif skel.ndim == 3 and skel.shape[-1] >= 3:
    joints = skel[:, :, :3] * 0.01
```

Three different extraction heuristics. If the wrong branch is taken (e.g., `>= 3` matches before `>= 16`), the extracted joints will be wrong. The `dataset_wrapper.py` has the same issue at lines 38-54.

## Diagnostic Script Plan

Create `MHRD-Pose/debug_skeleton.py` that:

1. **Loads a sample from the dataset** and extracts all relevant fields.
2. **Computes GT SMPL joints** from GT MHR vertices (barycentric path) → prints joint positions.

5. **Runs the model forward** (if checkpoint provided) and compares predicted vs GT SMPL joints.
6. **Computes the barycentric mapping error** by rendering the MHR mesh and checking if SMPL joint projections align with GT 2D keypoints.
7. **Prints coordinate system diagnostics** — vertex ranges, joint ranges, pelvis positions, etc.

## Fix Strategy

### Fix 1: Align MHR Skeleton with SMPL Joint Ordering
Ensure the first 24 MHR skeleton joints (or a selected subset) correspond to SMPL joint anatomy. If not, use only the barycentric SMPL joint path and ensure the mapping is accurate.

### Fix 2: Fix GT 3D Keypoint Computation
Instead of computing GT SMPL joints from GT MHR vertices (indirect, error-prone), compute GT SMPL joints directly from the original SMPL data (before MHR conversion). This ensures the 3D keypoint loss uses accurate SMPL joint targets.

### Fix 3: Fix Preconversion skel_state Extraction
Determine the actual skel_state format from the MHR model and use a single, correct extraction path. Remove ambiguous fallbacks.

### Fix 4: Fix Debug Vis Global Orient Application
Don't apply SMPL global_orient to MHR vertices. MHR vertices are already in the canonical body frame. The renderer handles orientation via camera translation.

## Critical Finding: Barycentric Mapping is the Root Cause

The `mhr2smpl_mapping.npz` is an **off-the-shelf mapping** loaded from the MHR package assets. It maps MHR vertices to SMPL joint locations via:
1. For each of the 6890 SMPL vertices, find the corresponding MHR vertex via barycentric interpolation of triangle coordinates
2. Apply SMPL's J_regressor (24×6890) to the interpolated vertices

This assumes MHR and SMPL have the **same body topology**, which they don't:
- MHR has 12826 verts (LOD1), 127 skeleton joints
- SMPL has 6890 verts, 24 skeleton joints
- The joint locations (hip, knee, elbow, etc.) may not align precisely

**Consequence**: The GT SMPL joints (derived from MHR vertices) are **systematically offset** from where the original SMPL model would place them. The model learns to match these wrong targets, producing "accurate-but-wrong" predictions.

## Fix Strategy

### Fix A (Recommended): Compute GT SMPL Joints from Original SMPLX Data
Instead of deriving SMPL joints from MHR vertices, compute them directly:
1. In `mhr_trainer.py` training step, run the original SMPLX model with GT pose/betas to get SMPLX vertices
2. Extract the first 24 body joints from SMPLX (same ordering as SMPL)
3. Use these as GT for `loss_keypoints_3d`

This avoids the barycentric mapping entirely for 3D keypoint supervision.

### Fix B: Recompute mhr2smpl_mapping.npz with Better Alignment
Use the MHR model's own skeleton to define joint locations:
1. Run MHR model in T-pose
2. Extract joint positions from skel_state
3. For each SMPL joint, find the closest MHR vertex position
4. Recompute barycentric coordinates around those vertices

### Fix C: Use MHR Skeleton for Both Pred and GT
Use `joints3d` (MHR skel_state) for both prediction and GT:
1. Fix the MHR skel_state extraction to use the correct format
2. Ensure the first N MHR skeleton joints match the required anatomy
3. This avoids SMPL entirely for keypoint losses

### Fix D (Quick): Disable 3D Keypoint Loss
Set `joint_loss_weight = 0` temporarily to verify that the other losses converge. If MPJPE improves, the issue is confirmed to be in the 3D keypoint GT.

## Priority Order

1. **Run diagnostic script** (`debug_skeleton.py`) → quantify barycentric mapping error
2. **Try Fix D** → disable 3D keypoint loss, check if other losses converge
3. **Implement Fix A** → compute GT SMPL joints from original SMPLX data
4. **Fix debug_vis rendering** → correct global_orient application
5. **Fix preconversion skel_state extraction** → single correct path, no ambiguous fallbacks

## Fix 1 — `_freeze_pretrained`: Wrong parameter name prefix

**File**: `mhr_trainer.py`

The original checked `name.startswith('model.model.')` but Lightning wraps the model in a single `model.` namespace, so all param names start with `model.`. Zero parameters were being frozen/unfrozen.

```python
# Before:
if name.startswith('model.model.'):
    bare = name[len('model.model.'):]
# After:
if name.startswith('model.'):
    bare = name[len('model.'):]
```

---

## Fix 2 — `configure_optimizers`: Same wrong prefix, separate occurrence

**File**: `mhr_trainer.py`

Same `model.model.` vs `model.` bug in `configure_optimizers`. The differential LR logic (lower LR for pretrained backbone, higher for regressor head) was silently not working.

```python
# Before:
bare = name[len('model.model.'):] if name.startswith('model.model.') else name
# After:
bare = name[len('model.'):] if name.startswith('model.') else name
```

---

## Fix 3 — `on_validation_epoch_end`: Wrong multi-dataset iteration

**File**: `mhr_trainer.py`

The multi-dataset branch iterated `for val in x` where `x` is a dict — this yields string keys, not values. It was silently silently producing wrong aggregation.

```python
# Before:
[val[ds_name + '_mpjpe'] for x in outputs for val in x]
# After (matching the single-dataset branch):
[x[ds_name + '_mpjpe'] for x in outputs]
```

## Fix 4 — `MHRRegressor hidden_dim`: 1024 → 32

**File**: `mhr_regressor.py`

`hidden_dim` had been set to 1024 but the pretrained checkpoint used 32 (original ReFit value). Shape mismatch caused all head weights to be skipped during `_load_pretrained_model`, so the model trained from scratch instead of fine-tuning.

Changed `hidden_dim=1024` → `hidden_dim=32` (line 147).

## Fix 5 — `init_cam`: Wrong initial camera scale

**File**: `mhr_regressor.py`

Initial camera was `[1.0, 0.0, 0.0]` but the original ReFit loads `0.9` from `SMPL_MEAN_PARAMS['cam']`. Using 1.0 gives slightly wrong initial projection scale.

```python
# Before:
init_cam = torch.tensor([[1.0, 0.0, 0.0]])
# After:
init_cam = torch.tensor([[0.9, 0.0, 0.0]])
```

## Fix 6 — Loss aggregation: Wrong formula when SUPERVISE_SEGM/DEPTH disabled

**File**: `mhr_losses.py`

The original formula is:
- If supervising segmentation/depth: `(body_loss * 10 + aux_losses) * loss_weight`
- Otherwise: `sum(loss_dict.values()) * loss_weight`

The MHR port was always using the `* 10` multiplier, producing 600× effective loss scale (LOSS_WEIGHT=60 × 10 = 600) instead of 60×.

Fixed to gate on `SUPERVISE_SEGM or SUPERVISE_DEPTH` flags, consistent with original.

**Note**: With `LOSS_WEIGHT=60`, enabling `SUPERVISE_SEGM` would create 600× scale. If that is ever re-enabled, set `LOSS_WEIGHT: 6` in config.

---

## Fix 7 — Validation joint protocol: No H36M-14 path

**File**: `mhr_trainer.py`

The original uses H36M-14 protocol for 3DPW/BEDLAM validation (matches published benchmarks):
1. Apply `J_regressor_h36m [17, 6890]` to predicted SMPL vertices → 17 H36M joints
2. Pelvis = h36m[:, 0]
3. Select `H36M_TO_J14 = [6,5,4,1,2,3,16,15,14,11,12,13,8,10]` → 14 joints

The MHR port lacked this path entirely. Fixed with three-tier fallback:
- Primary: H36M-14 via `J_regressor_h36m` (when file exists)
- Secondary: SMPL-24 fallback (when H36M file missing)
- Tertiary: MHR skel_state index mapping (when no `pred_smpl` available)

**Note**: `data/utils/J_regressor_h36m.npy` does not currently exist in the repo. The fallback SMPL-24 path is active. PA-MPJPE numbers are slightly incomparable to published benchmarks until H36M file is added.

---

## Fix 8 — 2D keypoint normalization: Already correct (no-op)

**File**: `mhr_losses.py`

The 2D keypoint loss normalizes predicted joints by `(IMG_RES / 2)` before computing loss (out-of-place, doesn't modify pred). This was already implemented correctly in the MHR port. No change needed.

---

## Fix 9 — Pose loss: Include global root transform dims

**File**: `mhr_losses.py`

The original SMPL regressor excludes `pred_pose[:, 0]` (global orient) from the pose regression loss because camera already handles global root position. The MHR port was not excluding any dims.

MHR `lbs_model_params` layout:
- `[0:3]` = global translation (moves all 126 joints)
- `[3:6]` = global rotation (moves 125 joints)
- `[6:]` = per-joint articulations

Excluding dims 0–5 avoids contradictory gradients between the camera head and pose head competing to place the root.

```python
# Before:
loss_regr_pose = criterion(pred_pose, gt_pose)
# After:
loss_regr_pose = criterion(pred_pose[:, 6:], gt_pose[:, 6:])
```

## Architecture Analysis: MultiLinear vs Flat MLP for MHR Regressor

**Question**: Should `MHRRegressor` use `MultiLinear(n_head=22)` like the original ReFit regressor?

**Answer**: No.

ReFit's `MultiLinear(n_head=22)` is valid for SMPL because SMPL has exactly 22 joints × 6D rotations = 132 independent per-joint parameters. Each head takes a [B, J, C] feature slice and predicts one joint's rotation in isolation — a clean structural match.

MHR's `lbs_model_params [204]` has **no clean per-joint decomposition**:

| Dims | Effect | Joints moved |
|------|--------|-------------|
| 0–2 | Global translation | 126 (all) |
| 3–5 | Global rotation | 125 |
| 6–23 | Compound spine/hip articulations | 89–92 each |
| 24+ | Increasingly local (fingers/toes) | Down to 1–2 |
| Active dims | 200 / 204 | |

204 / 22 = 9.27 — splitting at arbitrary boundaries mixes entangled hierarchical parameters across heads, destroying physical meaning. **Keep the flat MLP.**

### Real Bottleneck: `hidden_dim=32 → 204 dims`

| Branch | Original capacity | MHR capacity |
|--------|------------------|-------------|
| Pose | 32 hidden → 6D/joint | 32 hidden → **204 dims** |
| Shape | 32 hidden → 11 betas | 32 hidden → 45 dims |
| Expr | (none) | 32 hidden → 72 dims |

The pose branch has 34× more output demand on the same hidden capacity vs the original. If training plateaus, increase `hidden_dim` specifically for the pose branch (128–256 is a reasonable range). Do **not** widen all four branches equally — shape/expr/cam are fine at 32.

**Current recommendation**: Wait for plateau evidence before changing. Training is progressing (97mm PA-MPJPE by epoch 31).
